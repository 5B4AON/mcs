# Android (Google Play) wrapper: step-by-step log

This is a record of every step that worked so far in publishing Morse Code Studio on Google Play (issue #145). Follow it from the top to rebuild the setup from scratch, for example on a new computer.

> **No secrets in this file.** Passwords, the keystore file and personal account details are never written here. The keystore and its password live only in the owner's password manager and in `~/keys/`. Everything in this file is safe to publish.

## How it works

The Android app is a **Trusted Web Activity (TWA)**: a very small Android app that opens the hosted web app (`https://morse-code-studio.web.app/`) full screen in Chrome, with no address bar. It is generated by Google's **Bubblewrap** tool.

- A **web release** (`npm run build` + Firebase deploy) reaches Android users straight away. No store upload is needed.
- A **wrapper release** (a new `.aab` uploaded to Play) is needed only when the Android shell itself changes: icon, name, colours, minimum Android version, Bubblewrap update and so on.
- Chrome shows the app without an address bar only when the site proves it owns the app. It does this with `/.well-known/assetlinks.json`, which lists the SHA-256 fingerprints of the app's signing certificates.

## Fixed decisions (do not change)

| Item | Value | Why it is fixed |
|---|---|---|
| Canonical origin | `https://morse-code-studio.web.app` | The app is bound to this domain through `assetlinks.json`. Changing it means a new Play listing. |
| Package name (application ID) | `app.web.morse_code_studio` | Play never allows it to change. |
| Launcher name | `MCS` | Can be changed in a later wrapper release. |
| Play account type | Personal | Requires a closed test with at least 12 testers for 14 days before public release. |
| Minimum Android version | 7.0 (API 24) | Required by Android Browser Helper 2.7.4, which Bubblewrap 1.27.0 uses. |
| Bubblewrap version | `@bubblewrap/cli@1.27.0` (always run it pinned through `npx`) | The same tool gives the same output on every rebuild. |
| Upload key alias | `mcs-upload` | Stored in `~/keys/mcs-upload.keystore` (outside the repo). |
| Privacy policy URL | `https://morse-code-studio.web.app/privacy.html` | Entered in Play Console and linked from Help 11.5. |

## Step 2: Prepare the web app (repo changes)

These changes do not alter how the app behaves. They must be **deployed to Firebase before `bubblewrap init`** (Step 4), because Bubblewrap reads the live manifest and downloads the icons from it.

1. **`firebase.json`**: the `"**/.*"` entry was removed from `hosting.ignore`. Without this, Firebase silently skips the `/.well-known/` folder and `assetlinks.json` is never published.
2. **`.gitignore`**: signing keys and build output are ignored: `*.keystore`, `*.jks`, `key.properties`, `signing.properties`, `*.aab`, `*.apk`, `*.idsig`, `/android-wrapper/**/build/`, `/android-wrapper/.gradle/`.
3. **Icons**: Android crops launcher icons into circles and other shapes. The normal icon is too close to the edge, so two extra icons were made:
   - `store/images/source/icon-maskable.svg`: full-square background, symbols scaled to 78% so they stay inside the central 80% "safe zone".
   - `store/images/source/icon-monochrome.svg`: symbols only, in white on transparent, for Android 13+ themed icons.

   They were rendered to PNG with ImageMagick:

   ```bash
   S=store/images/source
   for n in 192 512; do
     convert -background none -density 1200 $S/icon-maskable.svg -resize ${n}x${n} -strip PNG32:public/icon-maskable-$n.png
   done
   convert -background none -density 1200 $S/icon-monochrome.svg -resize 512x512 -strip PNG32:public/icon-monochrome-512.png
   ```

4. **`public/manifest.webmanifest`**: the `maskable` entries point to `icon-maskable-192.png` and `icon-maskable-512.png`, and a `monochrome` entry was added. The normal `icon-192.png` / `icon-512.png` (purpose `any`) stay: Chrome needs them to treat the app as installable, and they are used unmasked on desktops and in install dialogs.
5. **`public/privacy.html`**: static privacy policy (no JavaScript), checked against the code: no accounts, analytics or tracking; microphone sound analysed on the device only; settings in local storage; the opt-in RTDB relay; Firebase Hosting request data; intended for users aged 13 and over (a TWA cannot target children under 13 under Play's Families policy).
6. **Help 11.5 "About and Privacy"** links to `/privacy.html`. Google requires the policy to be reachable inside the app as well as from the listing. The Creative Commons badges in the Help footer were copied to `public/help/cc/` so Help loads nothing from other websites.
7. **`public/.well-known/assetlinks.json`**: created as `[]` for now. The fingerprint is added in Step 7.

Check the build, then deploy:

```bash
npm run build
ls -a dist/morse-code-studio/browser/.well-known   # must list assetlinks.json
# deploy with Firebase as usual (owner only)
```

After deploying, check that these load in a browser:

- `https://morse-code-studio.web.app/manifest.webmanifest` lists `icon-maskable-512.png`
- `https://morse-code-studio.web.app/.well-known/assetlinks.json`
- `https://morse-code-studio.web.app/privacy.html`

In Chrome DevTools → Application → Manifest, tick "Show only the minimum safe area for maskable icons". Two icons are listed per size: the `any` icon touches the circle (that is expected, it is never masked), and the maskable icon fits inside it.

## Step 3: Tools

The machine already had Node and ImageMagick. Bubblewrap is run through `npx` (a global `npm i -g` failed because `/usr/local` belongs to root, and `npx` keeps the version pinned anyway):

```bash

```

Bubblewrap asks questions, so it must be run in a normal terminal (not in a non-interactive script). On its first run it offers to install its own **JDK 17** and **Android SDK** into `~/.bubblewrap/` (about 1 GB). Answer **Yes** to both and accept the SDK terms. The system Java is not touched, and Android Studio is not needed. The locations are recorded in `~/.bubblewrap/config.json`.

```bash

```

## Step 5: Correct the generated settings

`bubblewrap init` left three things that were changed by hand in `android-wrapper/twa-manifest.json` (the source of truth for Bubblewrap):

| Field | Generated | Changed to | Reason |
|---|---|---|---|
| `enableNotifications` | `true` | `false` | It added the Android `POST_NOTIFICATIONS` permission. The app sends no notifications, and it should ask for nothing it does not use. |
| `themeColorDark`, `navigationColor`, `navigationColorDark`, `navigationDividerColor`, `navigationDividerColorDark` | `#000000` | `#1A1A2E` | The system bars match the app's background in both light and dark mode. |
| `minSdkVersion` | `21` | `24` | The build failed: Android Browser Helper 2.7.4 needs API 24 (Android 7.0). Forcing it lower could crash on old phones. |

After editing `twa-manifest.json`, regenerate the Android project from it. Never edit the generated files under `app/` by hand: the next `update` overwrites them.

```bash
cd ~/code/mcs/android-wrapper
npx @bubblewrap/cli@1.27.0 update --skipVersionUpgrade
```

`--skipVersionUpgrade` keeps the version code unchanged. Without it, `update` increases it.

Quick checks that the changes reached the Android project:

```bash
grep -c POST_NOTIFICATIONS app/src/main/AndroidManifest.xml   # 0
grep -n minSdkVersion app/build.gradle                         # 24
./gradlew :app:processReleaseMainManifest --no-daemon          # BUILD SUCCESSFUL (no password needed)
```

Known limitation: Bubblewrap 1.27.0 does not put the monochrome icon into the Android adaptive icon, so Android 13+ themed-icon mode shows the normal icon. This is accepted rather than patched.

## Step 6: Build the signed app

```bash
cd ~/code/mcs/android-wrapper
npx @bubblewrap/cli@1.27.0 build
```

- Enter the keystore password at both prompts (see the note in Step 4).
- If it asks to apply changes from the web manifest, answer **No**: `twa-manifest.json` is already correct.
- The first build downloads Gradle and the build tools and takes a few minutes.

It creates (all gitignored):

| File | Purpose |
|---|---|
| `app-release-bundle.aab` | Uploaded to Google Play |
| `app-release-signed.apk` | Installed directly on a phone for testing |
| `app-release-unsigned-aligned.apk`, `*.idsig` | Intermediate files, not used |

Check the signed APK: package name, version, permissions and signing certificate (no password needed):

```bash
BT=$(ls -d ~/.bubblewrap/android_sdk/build-tools/* | tail -1)
$BT/aapt2 dump badging app-release-signed.apk | grep -E "^package|sdkVersion|uses-permission"
$BT/apksigner verify --print-certs app-release-signed.apk | grep SHA-256
```

The only permission listed should be `app.web.morse_code_studio.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`, an internal Android permission with no user prompt.

## Step 7: Publish the upload key fingerprint

Bubblewrap did not print the fingerprint. It was read from the signed APK with `apksigner` (command above). A certificate fingerprint is public: it is inside every APK you sign.

Upload key SHA-256:

```
F8:43:1F:4D:95:3A:13:8B:CB:ED:41:50:B6:F4:CA:B8:17:E6:08:CA:D9:27:26:0A:88:37:51:5D:92:C8:0B:50
```

`apksigner` prints it in lower case without colons. Convert it to the `assetlinks.json` format like this:

```bash
echo <lowercase-hex> | tr a-f A-F | sed 's/../&:/g; s/:$//'
```

`public/.well-known/assetlinks.json` now contains:

```json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "app.web.morse_code_studio",
      "sha256_cert_fingerprints": [
        "F8:43:1F:4D:95:3A:13:8B:CB:ED:41:50:B6:F4:CA:B8:17:E6:08:CA:D9:27:26:0A:88:37:51:5D:92:C8:0B:50"
      ]
    }
  }
]
```

The same fingerprint can be checked against the keystore (asks for the password):

```bash
~/.bubblewrap/jdk/jdk-17.0.11+9/bin/keytool -list -v -keystore ~/keys/mcs-upload.keystore -alias mcs-upload | grep SHA256
```

**Later (done in Step 12):** after the first upload to Play with Play App Signing, Play re-signs the app with its own key. Its SHA-256 was **added** to the same list. The upload key fingerprint stays too, so sideloaded test APKs still work. A missing Play fingerprint is the usual cause of an address bar appearing in the store-installed app.

Then deploy (`npm run build` + Firebase deploy) and check with Google's tool at <https://developers.google.com/digital-asset-links/tools/generator> (domain `morse-code-studio.web.app`, package `app.web.morse_code_studio`, the fingerprint above).

## Step 8: Connect a phone with USB debugging

Copying the APK to the phone through the Linux file manager (MTP) failed with "cannot write to mapped folder". Installing with `adb` over USB works instead and needs no file copy. `adb` is already part of Bubblewrap's Android SDK, so nothing extra is installed. These steps were done on a Samsung Galaxy; other phones use similar menu names.

1. **Turn on Developer options** on the phone: Settings → About phone → Software information, tap **Build number** 7 times and enter the PIN if asked. The phone shows "Developer mode has been enabled".
2. **Turn on USB debugging**: Settings → **Developer options** (a new entry near the bottom of Settings) → switch on **USB debugging**.
3. **Connect the phone** with a USB cable that carries data (not a charge-only cable) and keep the phone unlocked. If nothing happens, pull down the notification shade, tap the USB notification and choose **Transferring files**.
4. **Start adb and allow this computer**:

   ```bash
   ~/.bubblewrap/android_sdk/platform-tools/adb kill-server
   ~/.bubblewrap/android_sdk/platform-tools/adb devices
   ```

   The phone shows "Allow USB debugging?" with the computer's key fingerprint. Tick **Always allow from this computer** and tap **Allow**.
5. **Check the connection**: run `adb devices` again. The phone must be listed with the word `device` after its serial number.

| `adb devices` shows | Fix |
|---|---|
| Empty list | USB debugging is off, the cable is charge-only, or the USB mode is "Charging only". `lsusb` shows whether Linux sees the phone at all. |
| `unauthorized` | Accept the prompt on the phone. If it does not appear: Developer options → **Revoke USB debugging authorisations**, then unplug and plug in again. |
| `no permissions` | Run the two commands from step 4 once with `sudo`. |

USB debugging can be switched off again after testing. Developer options stay available for next time.

## Step 9: Install the signed APK on the phone

With the phone connected as in Step 8:

```bash
cd ~/code/mcs/android-wrapper
~/.bubblewrap/android_sdk/platform-tools/adb install -r app-release-signed.apk
```

- `-r` replaces an app that is already installed and keeps its data, so the same command installs every new test build.
- Expected output ends with `Success` (adb may say "Performing Incremental Install" first; that is normal). The **MCS** icon then appears in the app drawer.
- If it fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, the installed copy was signed with a different key (for example a copy from Play). Remove it first with `adb uninstall app.web.morse_code_studio`, then install again.

Result of the first phone test (Samsung Galaxy): no address bar, correct icon, dark splash, microphone, MIDI/serial availability and the relay all worked.

### Finding: the launch looks very quick (accepted, no change)

The big logo seen at launch is replaced by the main screen almost at once. Raising `splashScreenFadeOutDuration` from 300 to 600 ms made no visible difference, so it was put back to 300 (the Bubblewrap default). A 60 fps screen recording of a cold launch showed why:

- The big logo is the phone's own app-opening animation (Samsung zooms the launcher icon to full screen), not the wrapper's splash, and the wrapper cannot change it.
- Chrome then shows a dark screen for about 150 ms and the app appears at once. The whole launch takes about 0.35 s.
- The page paints so fast (served from the service worker cache) that Chrome removes its splash with no visible fade, so the fade setting has no effect.

Making the splash last longer would need a native splash with a forced delay, which Bubblewrap overwrites and Android's guidelines advise against. A fast launch is preferred, so this is accepted as normal.

To measure a launch again (phone unlocked, on the home screen; this only restarts MCS):

```bash
ADB=~/.bubblewrap/android_sdk/platform-tools/adb
$ADB shell am force-stop app.web.morse_code_studio
($ADB shell screenrecord --time-limit 7 /sdcard/Download/mcs-launch.mp4 &); sleep 1.5
$ADB shell am start -W -n app.web.morse_code_studio/.LauncherActivity   # prints TotalTime in ms
sleep 7; $ADB pull /sdcard/Download/mcs-launch.mp4 /tmp/ && $ADB shell rm /sdcard/Download/mcs-launch.mp4
```

Then step through `/tmp/mcs-launch.mp4` frame by frame in a video player (or split it into frames with `ffmpeg -i /tmp/mcs-launch.mp4 -vf fps=60 frame%04d.png`).

**Finding:** a new app's first release takes time to become installable even after it shows "Available". For about 15 minutes, the Store page showed "Item not found", then "Something went wrong on our end" and "The item that you were attempting to purchase could not be found", switching back and forth. Nothing needed changing.

What happened in order:

1. While waiting, the owner tried installing with adb. The phone refused and said the app must be installed from the Play Store. This is most likely the **automatic protection** chosen when the app was created: it blocks copies that were not installed by Play.
2. Back in the Play Store, the page now showed an **Update** button instead of Install. Tapping it installed the app.

It is not certain which of these fixed it: Play simply finishing after enough time, or the adb attempt followed by an update through Play. Most likely it was just time.

## Releasing a new wrapper version later

```bash
cd ~/code/mcs/android-wrapper
# edit twa-manifest.json if needed, then:
npx @bubblewrap/cli@1.27.0 update      # increases appVersionCode by 1
npx @bubblewrap/cli@1.27.0 build
```

Upload the new `app-release-bundle.aab` in Play Console. The wrapper version (`appVersionCode` / `appVersionName` in `twa-manifest.json`) is independent of the web app version in `package.json` and `version.ts`.
